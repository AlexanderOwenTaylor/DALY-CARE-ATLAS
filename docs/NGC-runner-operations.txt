DALY-CARE Atlas 73 — operating instructions

1. Extract the entire source runner ZIP into one writable folder inside NGC. Keep R/, scripts/, config/, inst/ and their contents together. Use the existing authorised DALY-CARE connection/bootstrap. Required R packages are listed in DESCRIPTION, including zip; arrange them locally before running. Terminology is packaged locally and the run does not download a release.

2. First run the short readiness check in RStudio:
   Sys.setenv(DALYCARE_ATLAS_PREFLIGHT_ONLY="TRUE")
   source("/path/to/DALY-CARE-ATLAS/RUN_DALYCARE_ATLAS_73_SOURCE.R", encoding="UTF-8")
   This checks schema and configuration, without full source profiling or website generation. logs/clinical_readiness.csv lists the missing prerequisites. logs/person-keys.review-required.csv is a worksheet: candidates are FALSE until their linkage is reviewed. Existing reviewed mappings remain recorded when their column is absent or schema cannot be checked; the evidence column reports the mismatch. Configured mappings are checked against schema, not assumed to establish actual person support.
   logs/encoding_diagnostics.csv contains finite code-token classes and distinct-person aggregate counts, with a 120-second overall probe budget and at most 15 seconds per probe (or a stricter configured timeout). Missing and conflicting people are separate. Unknown text is counted as other_nonempty; no patient identifiers or free-text examples are written. Budget-skipped probes are explicit. Keep all these files inside NGC.
   Review source codebooks and stored-unit metadata there. A token such as TRUE or 1 does not by itself prove treatment occurred. No units or clinical codes are inferred by the check.

   For full collection, clear the flag and source the same runner:
   Sys.unsetenv("DALYCARE_ATLAS_PREFLIGHT_ONLY")
   source("/path/to/DALY-CARE-ATLAS/RUN_DALYCARE_ATLAS_73_SOURCE.R", encoding="UTF-8")
   The default source map is config/source-map.dalycare73.tsv and default output folder is atlas_runs/. To change those, set DALYCARE_ATLAS_SOURCE_MAP or DALYCARE_ATLAS_OUTPUT_ROOT before sourcing. The 73 entries include helper/manual resources; the completion report states which were actually available and assessed.

3. Check the printed run directory and phase/completion reports. Collection, interpretation, website generation and packaging have separate outcomes. A working website or ZIP may still be partial. Inspect each field's reason rather than treating withheld, unrecognised, unassessed or legacy-unknown results as absence.

4. Keep the entire internal run, including outputs/ and logs/, inside NGC. Only the validated site.zip is the sharing package; its public-manifest.json lists the included assets and checksums. Extract all of site.zip before opening DALYCARE_atlas.html, or host that complete folder on a static web server. Do not share the internal run directory, R workspace/history or diagnostics.

5. To rebuild from retained aggregate CSVs without database access, use the original run directory and the complete current source project:
   Rscript scripts/rebuild_atlas_from_outputs.R "/path/to/run" "/path/to/project"
   Run from a terminal with Rscript available. Local reviewed unit/band resources needed by that export must still be configured. A website bootstrap JSON is not a substitute for the original outputs. A replacement site is promoted only after validation; a previous valid ZIP remains if packaging fails.

6. For a failed run, use the printed atlas_build_status.tsv and atlas_recovery.txt paths. Startup failures can have a recovery directory without a run directory. Keep diagnostics internal. Repair the named dependency/configuration/destination first; if collection completed, use the offline rebuild rather than repeating database queries.

7. Review local configuration before a new NGC run. DALYCARE_REGISTRY_PERSON_KEYS_FILE identifies reviewed exact source/key columns; identifiers are used internally for distinct-person counts and are not exported as values. DALYCARE_DATE_FORMATS_FILE supplies reviewed exact-field formats; a parsing rule does not establish the clinical event meaning. Numeric publication requires both DALYCARE_REGISTRY_UNIT_EVIDENCE_FILE and DALYCARE_REGISTRY_NUMERIC_POLICY_FILE with verified stored units and approved fixed bands. See docs/registry-summary-v2-contract.txt for the numeric policy and unit-evidence JSON schemas. Set DALYCARE_MIN_CELL_COUNT to any stricter local threshold; the minimum is five, and numeric summaries need at least 20 eligible people. Do not attest units or mappings from a familiar label alone.

8. Local and CI validation cannot establish live source behaviour. The next NGC run must confirm actual treatment encodings, stored-unit evidence, date formats, person-key availability and production queries. Missing source data and legitimately withheld results remain limitations. The release report separately records hosted, offline-loader and actual double-click browser validation.

Local CSV configuration (UTF-8)
Person keys: table_name,person_key,reviewed. Use one exact existing key column and reviewed=TRUE. The example config/registry-summary-person-keys.example.csv intentionally has blank keys and FALSE; do not use it unchanged as an attestation. Without a local mapping, the three reviewed RKKP registries, patient and SDS_pato default to patientid. The latter two reuse the documented high-confidence count linkages in config/mcl_triangle_person_date_mapping.tsv. SP_VitaleVaerdier still requires an explicit reviewed mapping: a column named patientid is a candidate, not sufficient linkage evidence. A supplied mapping is authoritative, including missing/disabled entries, and must cover every intended source needing person support.
Date formats: table_name,column_name,format_rule,reviewed; optional sentinel_dates. Allowed reviewed rules: iso, dmy_dash, dmy_slash, dmy_dot, ymd_compact. Sentinel dates are reviewed YYYY-MM-DD values separated by semicolons. No file means strict ISO parsing. Never guess formats or units from labels or old counts.
